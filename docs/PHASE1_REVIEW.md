## 需要修复

1. **运行清单可把失败原始响应计入成功覆盖。** `pipeline.load_run` 使用 entry.status 判断成功，
   对 raw 只核对摘要、API、参数与行数，没有核对权威原始状态、错误码、source 和 SDK。
   主审将一个真实结构的离线 fixture 保存为 provider_error / 10001011，并在 entry 中写 complete，
   读取器仍返回 complete=true、一个成功请求。恢复路径也仅检查引用摘要，须一起拒绝这类矛盾。
   修复应覆盖失败、部分响应、来源 / SDK 不一致及合法成功空返回，并保留有明确依据的 Phase 0 兼容。
2. **读取时没有绑定嵌入计划与原计划摘要。** `load_run` 从 run.plan 重算预期查询，但不检查
   plan_sha256 对应的原始计划。删改嵌入计划可能将原有缺失请求从分母移除。
   应保存 / 验证可追溯的原计划；已有 run 的兼容必须核对仍保留的原计划并显式处理，
   不能通过重新计算新摘要掩盖旧清单差异，也不重写原始运行证据。

第一项复现产物在主仓库 `.cache/phase1/main-review/provenance-i9koquqp/`，全程离线。
初次运行定位到默认环境未加载 worktree 源码，随后指定该源码；一次含中文路径的 stdin 脚本
遇到 PowerShell 编码错误，改为从当前目录推导根目录后完成。它们是主审脚本问题，不是数据服务错误。
